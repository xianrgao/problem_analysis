# 问题分析一般思路

以证据驱动调查循环：明确问题 → 找规律 → 形成可证伪假设 → 验证 → 回顾原问题。调查结论必须区分“观察事实”“关联线索”“待验证假设”“已验证原因”。

## 入口与计划边界

1. 读取用户请求和当前会话状态，确认区域、工站、时间范围、失效 task／parameter 或具体表现。可从已有上下文或变量目录获取的信息不重复询问；缺少会改变查询范围的信息时再澄清。
2. 首次路由只加载本技能。查看变量 `skills` 和 `host_capabilities` 决定可执行能力，不在正文维护技能元数据副本。
3. 按 [调查手册](references/investigation.md) 覆盖规律挖掘方向，形成 skill 级 DAG。通过计划接口提交并等待用户批准，批准前不执行跨技能调查。单次工具取数用于明确用户请求时遵守宿主当前授权范围。
4. 内部与用户计划共用步骤 ID：内部记录 skill／工具、依赖、输入变量引用和产物；用户计划只说明要查什么、比较什么及预期结果。
5. 已批准计划必须锁定版本。内部统计计算、SQL 修复不改变其范围；新增技能节点、扩大调查范围或改变问题假设需要新的计划版本。

## 执行循环

- 每一步开始前说明目的和行动，使用一句客观专业表述，例如“为判断失效是否集中在开班阶段，正在查询不良件的上线时间并对比早晚班首小时的占比。”不使用第一人称或“目的／行动”标签。
- 查询返回后使用真实的 `variable_name` 与版本引用；查看 preview 理解结构，代码读取完整数据。保存 SQL、代码、结论和图表的来源关系。
- 对照 [证据规范](references/evidence.md) 记录分母、去重粒度、时间边界、缺失与未覆盖数据。未发现规律也是合法结果，不挑选最大值强行解释。
- 根据已完成节点更新证据与假设，不以内部自由循环替代用户确认的计划。技能内部工具 DAG 不需再次确认，形成新 skill 级 DAG 则必须确认。
- 规律明确后提交深入验证计划：批次方向比较同期 OK／NC 全量数据；设备方向检查结构对应的变化点、过程参数与现场验证。
- 计划完成后检查原问题：是否解释影响范围、主要线索、证据强弱、建议验证动作？未完成时给出明确缺口或下一阶段计划，不能将“步骤跑完”当成“根因已确认”。

## 输出

调查摘要至少含范围、关键事实、已排查方向、最有支持的假设、反例／不确定性、下一步及证据变量引用。用户没有授权实际生产操作时，维修、更换备件、修改参数仅作为建议记录。
